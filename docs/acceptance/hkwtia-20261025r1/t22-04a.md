## Persistence contract

0066_application_supplements.sql follows 0065 from the starting checkout. Drizzle schema, snapshot and journal are committed together. It adds request/response tables and feature-scoped receipts; audits use existing audit_events. No existing application/profile/company record is backfilled or rewritten.

The adapter takes server-derived transaction scope from the service. It rejects absent scope before loading a database, uses an actor advisory transaction lock for cross-application idempotency, then locks the application row for lifecycle checks and transitions. It loads only that application's history; a member scope cannot load another applicant's private rows into the port. Two distinct staff actors therefore serialize on the application row independently of the actor lock. The partial unique index on application ID for published/responded independently rejects direct SQL violations.

Receipts have primary key (actor, operation_request_id) and retain operation kind, application/request references, payload hash and saved result. Responses have unique applicant/operation and request/version keys. Request transitions update only status, version, publication/closure timestamps and cancellation reason; published prompt content is not rewritten. Request/response changes, receipt and metadata-only audit events commit together. Audit metadata contains operation kind, never prompts, answers or staff context.

The service still owns authorization, version checks, input bounds, URL policy and explicit member projection. Fake transaction tests remain green. The SQL adapter has no default instance, session loader, Server Action or provider. Reads preserve database failures as failures rather than inventing missing records. Text timestamp fields retain the existing port's serialized date contract.
