# WTIA Platform contributor guide

## Stack and defaults

- Next.js App Router with TypeScript strict mode, Tailwind CSS, shadcn/ui, and `next-intl`.
- Server Components are the default. Add `'use client'` only for interactive browser behavior.
- Every user-visible string belongs in `messages/en.json` and `messages/zh-HK.json`; keep the bundles in parity.
- Do not add secrets to source control. Use `.env.example` for names only and `process.env` at runtime.
- Keep database and integration work server-side; M1 runtime configuration owns the Neon, Auth, and Stripe server credentials. Keep those modules server-only.
- `lib/db/schema-core.ts` is Drizzle's build-time schema; runtime server code imports `lib/db/server-schema.ts`, and client modules never import the core directly.

## Commands

```sh
npm install
npm run dev
npm test
npm run test:e2e
npm run audit:strings
npm run lint
npm run typecheck
npm run build
npm run db:migrate
npm run db:seed
```

`db:migrate` runs Drizzle migrations through `scripts/db-migrate.ts`; `db:seed` runs the idempotent M1 plan seed through `scripts/db-seed.ts` (with `db:seed:m1` available for the direct runner). Keep `DATABASE_URL` in the environment and never print it.

`db:seed` runs the M1 plan seed and then the deterministic M2 demo seed. `db:seed:m2` runs only the M2 fixture layer with `node --experimental-strip-types`; migrate and seed M1 first when using it directly.

`db:seed:m6` is the separately guarded Launch Pad acceptance fixture. It requires
`M6_ACCEPTANCE_SEED=true`, equal `DATABASE_URL`/`DATABASE_URL_TEST` values, and
an exact `M6_ACCEPTANCE_DATABASE_HOST_ALLOWLIST` entry for an explicitly
allowlisted, non-Production database hostname. The guard blocks Production-mode
execution and unallowlisted hosts, but it cannot establish that a host is
isolated; the operator must confirm the selected database is isolated before
seeding.

## Conventions

- Use strict TypeScript and avoid `any` unless the code includes a reasoned comment.
- Prefer typed content contracts over fabricated data or client-side fetching for public pages.
- Use conventional commits: `feat:`, `fix:`, `test:`, `chore:`, or `docs:`.
- Run the focused test, full unit suite, lint, typecheck, and build before handing off a change.
- Keep accessibility landmarks, skip navigation, keyboard focus, and localized recovery states intact.
- Work test-first. Write the test, **run it, and read the failure** before writing the code that
  satisfies it. Watching it fail is the part that carries the value: a test that has never failed is
  a claim, not evidence. Two assertions in this repo had silently stopped testing anything —
  `m4b-runtime-guard` compared a position against `indexOf("serverEnv()")` after that call was
  renamed, so it asserted `112 < -1` and became unsatisfiable, and a slightly different refactor
  would have made it vacuously *pass* instead. Confirm the failure names the behaviour you meant,
  not a typo, a missing import, or a `-1`.
- A test that guards an invariant should prove it can still catch a violation. The established
  shape for this is `server-action-actor-boundary.test.ts`: it discovers its own targets, asserts a
  minimum count so a broken walk cannot pass vacuously, and carries a `detects the shapes it is
  meant to catch` case with hostile and safe samples. Reuse that shape for boundary and discovery
  tests, and when adding one for a bug that reached `main`, reintroduce the bug once to watch the
  new test fail.
- Prefer assertions on behaviour over assertions on source text. Where a source-level check really
  is the only option, anchor it on the property that matters — any `*Env()` accessor, a property
  name — rather than one spelling that a rename will quietly retire.

## Task 11 database setup

Create an isolated Neon branch/database for migration and seed verification. Put its pooled connection string in `DATABASE_URL_TEST` only in the local test environment; never commit or print the value. Run `npm run db:migrate` before `npm run db:seed`.

The combined seed writes the four stable plan rows (`community`, `startup`, `corporate`, and `patron`) followed by the M2 demo contract: exactly 30 non-personal `.example.test` profiles, 12 companies, one staff, one ExCo, one superadmin, varied member histories, four events, saved segments, one queued campaign, and pending approvals. The fixed M2 reference instant is committed in `scripts/seed-m2.ts`; the engineered corporate segment and production at-risk query return exactly `m2-risk-01`, `m2-risk-02`, and `m2-risk-03` in renewal order when evaluated at that instant. Mutable fixture rows use idempotent upserts and immutable history rows use stable IDs with conflict-ignore semantics, so a second run creates no duplicates.

Use only an isolated `DATABASE_URL_TEST` for M2 migration/seed acceptance. With no test URL, the acceptance suite skips; `RUN_POSTGRES_INTEGRATION=1` opts into a disposable local PostgreSQL 16 container. Never point fixture commands at production.

For Stripe test-mode acceptance work, use test-mode values for `STRIPE_TEST_SECRET_KEY`, `STRIPE_TEST_WEBHOOK_SECRET`, `STRIPE_TEST_STARTUP_PRICE_ID`, and `STRIPE_TEST_CORPORATE_PRICE_ID`. Keep production Stripe variables separate and do not use live keys against the test database.

- Phase B2, three findings worth more than the feature. First, **`exists()` in Drizzle only parenthesises a `Subquery` object** — it is literally ``sql`exists ${subquery}` ``, so the raw `sql` fragment every one of these repositories passed it was pasted in bare and rendered `... and exists SELECT 1 FROM …`. Postgres's grammar is `EXISTS select_with_parens`, so that is a syntax error: *every* member-actor call into `companies`, `memberships`, `applications` and `billing_attempts` threw at the database rather than running, and `/portal/company` could not save at all. Fail-closed rather than a bypass, and it predates the branch (`1132d5d`). Nothing in the suite could catch it, because every assertion was on generated SQL **text**, which renders the broken form as happily as the working one, and no unit test runs a statement against Postgres — `tests/unit/repository-exists-scope-sql.test.ts` now drives all eight member-scoped predicates through the proxy driver and requires balanced parentheses after every `exists`. Second, **a scheme check is not a URL policy**: `publicWebsiteUrl` claimed to be `canonicalHttpsUrl`'s rule minus the query clause and had quietly dropped four more — userinfo, explicit port, localhost and IP-literal hosts, and the length bounds — so `https://wtia.org.hk@evil.example/login` was storable, rendered verbatim in the member page's anchor and in the JSON-LD `sameAs`, and shown to the staff reviewer, who is the person that host is aimed at. The policy now has one owner with an `{allowQuery}` option, and the review queue's projection runs the same rule so the queue is a true preview. Third, **on a public detail page a `.catch(() => null)` is not a safe default**: it collapses a transient database outage into a 404, and a 404 tells a crawler to drop a reviewed member page where a 5xx only asks it to retry. `/members/[slug]` awaits its read bare and calls `notFound()` only on a genuinely `null` row; the catch belongs in `generateMetadata` alone, which has an honest branded fallback. `/showcase/[slug]` draws the same line and `tests/unit/member-detail-page.test.tsx` pins it.

- Phase C1 — the WhatsApp human lane: a prospect messages the WTIA number, the concierge answers, and staff can now take the thread over in `/admin/inbox` and reply inside the 24-hour customer-service window. `conversations` and `messages` stop being bot transcript artefacts and become operational records — migration 0031 gives a conversation a `channel`, a `handling` state (`bot`/`human`/`closed`), an assignee, a contact link and `last_inbound_at`, and gives a message a `direction`, a `delivery_status`, a sender, a template key and an idempotency key; 0032 backfills them. **The two files are one unit**: 0031's new conversation-reuse predicate is only as inclusive as the old one *because* 0032 backfills `channel`, so applying 0031 alone opens a second conversation per person on the first inbound after deploy — splitting exactly the threads the inbox exists to unify. Staff replies go through new actor-taking methods on `inboxRepository`, never `conversationsRepository`, whose every write is gated by a `ConversationOwner` an admin would have to forge; the send is write-ahead — one `queued` row plus one `conversation.reply.queued` audit row in the same transaction, then the adapter, then a settle — and both retention sweeps learned about `handling`, so a staff↔member thread is no longer deleted out from under its own audit trail. - Phase C1, the part worth reading before anyone debugs it: **one send is not one row, and one row is not one send.** A deterministic `outbound_key` plus a partial unique index makes a double-submitted draft a single `messages` row — but in the naive design both submits still reached the adapter, so the member got the message twice, and the same hole reopened after any crash between the adapter returning and the settle committing, because the row stays `queued` and `queued` is the re-send state. Idempotency is therefore two mechanisms: the key dedupes the row, and a two-minute `send_claim_expires_at` lease dedupes the *send*, through a guarded `UPDATE` that lets a caller inherit an abandoned claim or re-queue a reply the provider definitively refused, and short-circuits before the adapter otherwise. Separately, `message_role` gains `'staff'` in 0031 and **no migration in this release may name that literal** — `drizzle-kit migrate` runs every pending file in one transaction and Postgres forbids *using* a new enum value in the transaction that added it, so a `DEFAULT 'staff'` would abort the whole deploy on a fresh database, at deploy time, invisibly to every incremental test. And `lib/db/repos/message-eligibility.ts` reads **both** consent stores, because `message_suppressions.profile_id` is NOT NULL — a contact can never be suppressed there, so a check that reads one store sends to somebody who said STOP. Marketing opt-in gates marketing only: `contacts.whatsapp_opt_in` is `false` for every prospect who has ever messaged us, so gating a service reply on it would block the only population Phase C exists to serve.
- Phase C1 consent review, three defects and one lesson: **the evidence a guard depends on can be spent by the caller.** `suppressionsRepository.optOutWhatsApp` treats the `whatsapp_opt_in` transition as the second, independent proof that a withdrawal is new — the suppression INSERT being the first, and it conflicts forever after the first STOP because nothing deletes a suppression row. But `lib/ai/woztell-webhook.ts` cleared the flag itself, unaudited, *before* calling it, so the transition was always already spent: a member who re-granted in the portal and said STOP again had both halves answer "already done" and the audit INSERT was skipped. A real withdrawal, invisible in `audit_events`, boundary 11 broken by the branch that fixed the same hole on the contact side. The webhook now calls `recordOptOut` first and `setWhatsappOptIn` after, where it is a no-op. The repository test that recorded the silent outcome called it "a Woztell redelivery" and so let the WhatsApp lane's genuine second withdrawal through CI wearing a redelivery's clothes; the two are now driven through the webhook and held apart in `tests/unit/woztell-consent-audit.test.ts`. Second, the bot lane's opt-in gate read `profile?.whatsappOptIn ?? true` — a sender with no profile was opted in by construction and `contacts.whatsapp_opted_out_at` was consulted nowhere, so a prospect who said STOP got a concierge reply the next week; it now asks `messageEligibility` through a webhook-capability door onto the *same* facts loader and precedence, and blocks on a consent answer only (`no_number` is a reachability fact about a stored column, and this lane replies into an open session on the number it already holds). Third, the portal and `/join` wrote a WhatsApp consent grant or withdrawal through a bare `UPDATE profiles`; `profilesRepository.update` now audits the **transition** — never the value, or every job-title correction would mint a consent event — inside the transaction, with `SELECT … FOR UPDATE` taking the row lock before the write so two concurrent saves cannot both audit.
- Phase C1 review, C-2 — **the reply lane dropped a staff reply that repeated an earlier sentence.** `outboundKeyFor` hashed the draft and nothing else; `messages_outbound_key_unique` is permanent; and C1 had just exempted human-handled and closed threads from both retention sweeps, so no row carrying one of those keys is ever deleted. The dedupe window was therefore unbounded in *time*. Monday's "Thanks — someone will come back to you shortly." settles `sent`; Wednesday the prospect writes again, staff send the identical line, the INSERT conflicts, the claim `UPDATE` refuses a settled row, the fallback SELECT answers `already_sent` and the send returns before the adapter — no message, no transcript row, no audit row. An inbox runs on canned replies, so that is the ordinary case. Nothing caught it because the acceptance spec timestamps its draft and every other test sends one distinct draft. The key now carries a **per-attempt token** the composer mints, keeps beside the draft in `sessionStorage` and rotates once a send reaches the provider: the window is one send attempt, not a span of time. Deliberately not a clock — every time bucket has an edge, a double-click that straddles it is the exact event the key exists to stop, and widening the bucket widens the span in which a deliberate re-send is swallowed. **Second half, and a separate bug:** `sendInboxReplyAction` flattened the `sent` / `already_sent` discriminator to `{status:"sent"}`, so the composer said "Sent." and cleared the draft — the last copy of the text — for a reply the adapter was never handed. `already_sent` is now its own state, its own string in both bundles, and rendered as a warning with the draft kept. **Third:** the three adapter codes that leave acceptance UNCERTAIN are excluded from `PROVIDER_REFUSED_SEND`, so the claim will not re-take those rows — yet they were reported under `DELIVERY_FAILED`, whose string invites a retry that answers `already_sent` while nothing is sent. `DELIVERY_UNCERTAIN` splits them, decided by `providerRefusedSend()` so the message and the statement that will answer the next click cannot disagree. **Fourth:** the two-minute send-claim lease was justified by a comment saying it exceeds the adapter's request timeout; `sendLive` called `fetch` with no `signal`, so the real bound was undici's ~300s header timeout and a hung send outlived its own claim. There is a real `WOZTELL_REQUEST_TIMEOUT_MS` now (built from `AbortController`, not `AbortSignal.timeout`, which jsdom lacks — a missing global would have made every live send a `retryable_network` failure), the lease is derived from `SEND_CLAIM_LEASE_MS`, and a test pins the order. **The lesson worth more than any of it:** adding `attemptId` to the reply input broke *every* reply in the product and no test noticed, because `queueStaffMessageSchema` is `.strict()` and both sides of that boundary substitute the other — the action's tests fake the repository, the repository's tests hand-write its input. `tests/unit/inbox-repeat-reply.test.ts` now drives the real `queueStaffMessage` from the real `sendInboxReply`, and the call site spells its argument out instead of spreading.
- Phase C1's provider assumptions, which are **not** verified and must not be read as though they were: there are no Woztell credentials, no captured payloads and no provider documentation in this tree. The delivery-status discriminator, the outbound-echo discriminator and the Open API GraphQL document (host, `conversationHistory` selection set, entry shape) are guesses, each confined to one function behind a zod parse that fails closed — an unrecognised payload is handled deliberately, never crashed into a Woztell retry loop. Every flow is exercisable through the mock adapter and no test needs a credential, which is the point; it also means the ticks arriving is untested against reality. Until somebody replays one captured real delivery-status payload and one outbound-echo payload through `normalizeInbound`, "the ticks do not arrive" is a normaliser bug first and a provider problem second, and nothing in the tree tells you which — the route answers 202 for every outcome and that layer logs nothing on purpose. The backfill's first real response carries a matching trap: its timestamp mapper accepts a string or a numeric epoch, and any other shape maps every entry to `null` and reports the whole backlog as `skipped`, which looks exactly like success. Both are tracked as O-1/O-2 in `docs/superpowers/plans/2026-09-10-phase-c1-whatsapp-human-lane.md`, whose exit checklist now separates what this branch executed from what only an owner with production credentials or live Woztell can.
- Phase C1 review, the third defect and the shape all three share. **A hostile provider field was a permanent retry loop rather than a refusal**: the route turns any throw into a 500 and Woztell retries a 500, and although the normaliser fails closed — its own comment says nothing there may throw — four zod length bounds sat *behind* it on strings that arrive straight from the provider (`whatsappMemberId` 200 in `lib/db/repos/contacts.ts`; `providerMessageId` 300, `errorCode` 200 and the outbound echo's `text` 20 000 in `lib/db/repos/woztell-inbound-events.ts`). One over-long value therefore looped that sender for ever: the message never persisted, never reached staff, and cost an invocation on every redelivery. The numbers moved to `lib/whatsapp/provider-field-limits.ts`, where the normaliser applies them before anything can throw, and the repositories keep enforcing the same numbers as a backstop for C-3's second entry point — shared deliberately, because a repository bound that drifted below the clamp would reopen the loop in silence. The four verdicts differ because the fields do: a provider message id is **rejected** in all three arms, since `messages_provider_message_id_unique` and every idempotency probe match it exactly and a truncated id settles or adopts *another message's* row; a WhatsApp member id is **dropped** to absent the way a blank one already is, because it is an optional adornment C1 reads nowhere while refusing the whole inbound would lose a real prospect's message and a truncated one links permanently to the wrong member; an error code is **truncated**, being diagnostic prose in an unindexed column that rides on the `failed` tick, so a reject rule would discard exactly the failures staff need; the echo body is **rejected**, because the adopt statement joins on message content and a shortened body cannot match its own row. A refusal is its own `NormalizedInbound` arm carrying its own reason rather than a fifth `unsupported_event`, because the response body is this subsystem's only observability and "we refused a hostile field" is not "we do not handle this event". **Now the part that outlives the three fixes: each was a guard whose answer had come loose from its effect.** `optOutWhatsApp` answered "already withdrawn" and wrote no audit row, because the caller had spent the transition the guard decides on; `outbound_key` answered `already_sent` — rendered as "Sent." with the draft cleared — for a reply the adapter was never handed; and the normaliser's fail-closed guarantee, recorded as fact in the bullet above this one, covered nothing at all for four fields, so the answer was a 500 inviting a retry that could never succeed. Two of them reported success while doing nothing and the third reported a failure it would never stop reporting; in all three the answer had stopped describing the work, which is why no amount of reading the *caller* would have found them. **And each survived CI in one of two ways, both of which are a test defect rather than a coverage gap.** Either the test asserted the wrong thing — `tests/unit/suppressions-whatsapp.test.ts` carried a case that recorded the silence and called it "a Woztell redelivery", so the WhatsApp lane's genuine second withdrawal passed through CI wearing a redelivery's clothes, a green assertion sitting on top of the bug — or the test was written around the collision: the C-2 acceptance spec timestamps its draft and every other reply test sends one distinct sentence, so the repeat that the unbounded dedupe window swallows was never once produced, and no webhook test crossed the seam where the bounds sit, because the normaliser's tests fake the repository and the repository's tests hand-write well-formed input, the same mutual substitution that let a `.strict()` schema break every reply in the product unnoticed. The three replacements are built the other way round, end to end through the real units: `tests/integration/woztell-hostile-provider-field.test.ts` drives the real route over the real normaliser, processor and repositories, `tests/unit/inbox-repeat-reply.test.ts` drives the real `queueStaffMessage` from the real `sendInboxReply`, and `tests/unit/woztell-consent-audit.test.ts` drives both withdrawal inputs through the real webhook. **Ask of a guard's test not whether it passes but what it asserts the guard DID; when the answer is only the status the guard returned, the test and the defect agree.**

# Codebase Knowledge Graph (codebase-memory-mcp)

This project uses codebase-memory-mcp to maintain a knowledge graph of the codebase.
ALWAYS prefer MCP graph tools over grep/glob/file-search for code discovery.

## Priority Order
1. `search_graph` — find functions, classes, routes, variables by pattern
2. `trace_path` — trace who calls a function or what it calls
3. `get_code_snippet` — read specific function/class source code
4. `query_graph` — run Cypher queries for complex patterns
5. `get_architecture` — high-level project summary

## When to fall back to grep/glob
- Searching for string literals, error messages, config values
- Searching non-code files (Dockerfiles, shell scripts, configs)
- When MCP tools return insufficient results

## Examples
- Find a handler: `search_graph(name_pattern=".*OrderHandler.*")`
- Who calls it: `trace_path(function_name="OrderHandler", direction="inbound")`
- Read source: `get_code_snippet(qualified_name="pkg/orders.OrderHandler")`
